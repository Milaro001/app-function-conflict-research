# 写作与可读性规范（N6—N7）

网页读者是产品、设计、运营同学，不是方法论审稿人。每段先让人一眼看懂“发现了什么、该做什么”，依据和边界放在后面、可展开。

## 每个议题的固定写法

| 位置 | 写法 | 长度 |
|---|---|---|
| `insight.headline` | 一句话结论，有动作、有对象，不写“可能”“或许”的连串保留 | ≤30字 |
| `insight.key_points` | 最多3条要点：①用户遇到了什么 ②最可能为什么 ③先做什么 | 每条≤40字 |
| `insight.confidence` | 高/中/低 + 一句理由；把“未复现、样本小、版本未知”等保留语集中在这里 | 理由≤40字 |
| 其他段落 | 先结论后依据；一段只讲一件事；超过3句改成列表 | 每句≤40字 |

`title`保留为完整的建议句（列表卡片用），`headline`是更短的首屏标题。限制条件只在`conditions`和`confidence`里出现一次，不要在每段句尾重复“尚未证实”“不代表普遍”。

## 用词：换成白话

| 不要写 | 改成 |
|---|---|
| 范围合格组 / qualified_in_scope | 完全符合本轮条件的反馈 |
| 语义候选 / 评论候选组 | 与功能相关的反馈 |
| 同文组 | 去掉重复后的反馈 |
| 反证任务 / disconfirming question | 怎么验证 |
| 待验证解释 / 假设 | 可能的原因（待验证） |
| 材料依据 | 用户原话 |
| 关系判断 / relation | 两种声音是什么关系 |
| 条件对齐 | 先确认是不是同一件事 |
| 单侧问题 | 目前只听到一种声音 |
| G2 / G3 | 你的判断 / 下一步选择 |
| P / V | 问题或改进诉求 / 认可或偏好 |

术语必须出现时，第一次后面跟一句括号白话解释。英文代码（P/V/conflict_candidate等）只出现在数据文件，不出现在网页正文。

## 句式

- 有主语：“菜鸟团队应……”“急着取件的用户……”，不写无主语的“需进一步核实”。
- 少否定：把“不能据此认定A，也不能推出B”改成“目前能确定的是C；A、B还要验证”。
- 数字带单位和分母：“20条相关反馈（来自6个平台）”，不写“20组”。
- 情绪只引用户原话，分析句保持平实，不评价用户。

## 自查清单（生成前逐项过）

1. 首屏只看headline和3条要点，能否说清问题与第一步？
2. 有没有一段超过4句话？有就拆成列表或卡片。
3. 有没有出现上表左栏的词？
4. 每条“原因”是否标了待验证，每个“方案”是否写了谁来做、怎么验证、做到什么算通过？
