# 后续文件的制作与检查

用户已选定格式时直接沿用，不重复确认。只制作当前请求中的文件；制作方式受主机真实能力约束。

## PPT

1. 找到并读取实际安装的 `consulting-deck-expert/SKILL.md`，建立决策对象、证据、主线和页图。
2. 找到并读取 `ppt-master/SKILL.md`，执行其完整性检查、路由、实际制作流程、适用确认与质量关卡，由其原生导出可编辑PPTX。用户明确委托设计选择时，记录为代理选择，不伪造用户确认回执。
3. 使用 `presentation-qa/SKILL.md` 检查最终文件，渲染全部页面，修正截断、覆盖、错误图示与证据不一致，并对改动页复查。
4. 文件由其他后端生成时，必须如实说明实际后端，不能称其由PPT Master制作。缺少上述Skill时先补齐依赖，或说明阻塞并保留材料，不静默换后端。

三个Skill在完整交付ZIP的 `bundled-skills/`。安装器将它们安装为主Skill的同级目录；从源码安装可运行本Skill的 `scripts/bootstrap_delivery_skills.py --install` 获取固定版本。随后按主机提供的Python执行PPT Master脚本；核心Python依赖可用 `--install-runtime` 安装到主Skill的私有环境。没有图像生成能力时，保留该工具要求的可用分支，不谎称已有图像服务。

## Word

目标主机提供这些Skill时，按其实际工作流使用：`build-report` 组织读者、问题、证据、分析和建议；`documents` 制作可编辑DOCX并渲染；`validate-data` 检查来源、数字和结论。

交付前逐项检查：重要结论是否有对应证据，事实与假设是否分开，章节是否承接前文，术语和主语是否清楚；最终文件逐页检查标题层级、分页、缺字、表格宽度和图文位置。不能只检查生成脚本。

如果其他Agent没有同名插件，先识别其真实文档能力。使用该主机的可编辑Word工具或受支持文档库，并明确记录工具名称、渲染是否完成及缺口。不得声称执行了不存在的Skill，也不得将HTML改扩展名充当DOCX。

## Excel

目标主机提供 `spreadsheets` 和 `validate-data` 时，实际执行它们的工作流。先定义每行的对象、每列的属性和主要阅读任务，再组织必要字段、分组和筛选。

检查单位、时间、分母、去重、缺失与零值、公式和合计。保留应当可重算的公式，合理设置列宽、换行、冻结表头与数字格式。不能把长报告塞入窄单元格，也不能靠过小字体让整张表勉强放下。重算并检查最终工作表的实际显示和错误值。

其他主机同样先检查真实表格能力，再使用其可编辑工作簿工具，记录实际后端。缺少公式计算或渲染能力时，交付边界要明确，不将未执行的检查标记为通过。

## 网页原型与分享

原型区分模拟状态、真实原文与待验证方案，按钮不得假装已扣款、发工单或完成用户测试。验证方案说明参与者条件、任务、观察项、建议通过标准与下一轮决策。

本地与公开分享使用不同交接方式：只有验证过的本机接收器能提交到当前对话；公开版默认导出任务文件，不能指向作者的私有对话。公开前移除登录资料、密钥、本机路径与私人接收器，保留必要原文和样本边界。

分别记录：部署是否成功、访问范围是否公开、普通匿名浏览器是否实际访问通过。403拦截、验证码或工具访问失败不伪装成通过，也不绕过访问控制。无法确认公网可用时，提供自包含离线HTML与迁移文件，并说明具体验证范围。
